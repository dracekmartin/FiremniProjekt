\section{Introduction}

The author works for M-line software as a software engineer, primarily on the EDISON product line, integrated into the team's standard development practices. The ``academic team'' for the project is this M-line development team. M-line is a Czech software company developing the EDISON information system for the transportation and logistics domain (public transport, payroll, timetables, and many other related agendas) on top of an InterSystems Caché backend with a Windows desktop client. The company plans an incremental modernization of the legacy .NET Framework + WinForms client onto a more modern stack of .NET Core + WPF.

The core goal of the project is to establish modern processes and an architectural foundation that subsequent in-house work will reuse. A concrete software piece -- a modernized client shell -- serves as both a working product and as a demonstration of the processes and patterns being introduced.

\medskip
\noindent The expected outcomes, as committed to in the approved project proposal (with the pilot criterion tightened since approval):

\begin{itemize}
  \item \textbf{Testing infrastructure} on both the .NET and the Caché side, establishing a test-first culture absent from the legacy stack.
  \item \textbf{Architectural foundation and reusable toolkit} for future agenda implementations, including a backward-compatibility layer that hosts legacy agendas.
  \item \textbf{Licensing modernization}: a new licensing data model and store, migration of the existing licenses into it, migration of the module tree definitions from XML files into the Caché backend, and the related internal tooling created or rewritten.
  \item \textbf{Update mechanism modernization} on both the client and the server side.
  \item \textbf{Modernized shell with a mini-app subsystem} and at least one demonstrative mini-app.
  \item \textbf{Pilot deployment} on developer workstations and at least one customer site switched fully to the new shell.
\end{itemize}

\noindent Section~\ref{sec:description} breaks these down into concrete requirements.

\subsection{Relation to other projects}
\label{sec:relation}

The project is being developed alongside several existing M-line projects with which it must coexist:

\begin{itemize}
  \item \textbf{Legacy EDISON} (VB/C\# .NET Framework WinForms) -- the production system currently running at customer sites. The modernized version will run against the same Caché backend, share the general idea of responsibilities and will incrementally take over selected agendas. No breaking changes to the legacy contract are permitted during the transition.
  \item \textbf{InterSystems Caché backend} -- the shared data store. It is used by most of the company's projects. Many of the project's architectural decisions will be influenced by the fact that our deployment process is much faster when deploying just a Caché update (and not the .NET). This is impossible to change, due to the non-negotiable compatibility with the old agendas. A concrete example of this is the licensing. However, many lower-level decisions, like those in the toolkit for developers, will also be influenced by this fact.
  \item \textbf{TemplateDesigner} -- a WPF agenda concerning documents (printable timetables, invoices, etc.), already written by a colleague partially in the new stack. It serves as a second consumer validating the toolkit design (alongside the shell itself); its needs will influence which parts of the toolkit are prioritized.
\end{itemize}

\section{Project description}
\label{sec:description}

\textbf{End users and functionality.} EDISON installations are operated primarily by Czech transportation and logistics companies, primarily public-transport providers. Daily users are back-office staff in roles such as dispatching, payroll administration, ticketing, and accounting. The system covers the operational lifecycle of a transport company, with currently around fifty agendas corresponding to specific business processes (fleet operations, scheduling, payroll, ticketing, asset management, subsidies, accounting, reporting, etc.).

\medskip
\noindent \textbf{Stakeholders and value.} The primary stakeholder is M-line software, the company developing and maintaining EDISON; the resulting foundation will be reused by in-house developers to migrate further agendas after the project ends. The secondary stakeholders are the customer organizations operating EDISON installations, who will benefit from the overall improvements in the development process (speed, testing) and will receive a more modern user experience.

\medskip
\noindent The new foundation and toolkit will make (re)implementing new agendas easier in a number of ways:
\begin{itemize}
    \item Testability reduces manual regression checking and protects against breaks during refactoring.
    \item The architecture will (at least partially) enforce testability and responsibility separation. This separation is especially murky in parts of the old codebase, which makes modifications to it very difficult.
    \item Mini-apps let agendas surface key state and tasks directly in the shell.
    \item The new stack will be much more supportive of AI coding assistants, both by the nature of the technologies used (WinForms UI definitions are a notorious problem) and the mentioned testability and architecture benefits.
\end{itemize}

Other than the benefits for the new agendas, the previously mentioned points that generally fall under the umbrella of the shell will be improved and will be rid of a number of pain points (which slow down development):
\begin{itemize}
    \item Modernization of licensing will allow us to extend the system for new features. But even the old functionalities will be made more user-friendly, with the users being:
    \begin{itemize}
        \item Developers, when they need to add or modify the relationships between modules that they have developed.
        \item Licenser (company employee creating/modifying licenses), who will be able to use a more modern tool to express the constraints coming from agreements with end users more easily. The tool will be more in line with other tools the company has recently developed.
    \end{itemize}
    \item Update mechanism modernization will allow improvements, or at least prepare the systems for it, because the old one is simply too tangled to be modified.
    \item The old shell has a number of tangled issues with user (in)activity which are effectively impossible to solve, and negatively impact the systems of licensing, updating and the agendas themselves.
\end{itemize}

\medskip
\noindent \textbf{Mini-apps.} The legacy shell has only a very limited capability of showing agenda information outside the agendas themselves. The mini-app subsystem addresses this: an agenda can publish small at-a-glance views (summaries, reminders, key tasks) that the shell displays without the user opening the full agenda. The feature targets power users who work across multiple agendas during the day and need a quick overview of their state. Mini-apps are opt-in per user: each user chooses in their settings which mini-apps to display. It is not a global or per-deployment choice.

\medskip
\noindent \textbf{AI-augmented development.} The project is developed with extensive use of AI coding assistants throughout. Rather than treating AI tooling as a passive convenience, the project will explicitly document the patterns and guardrails that make it productive: project memory in the form of in-repo guidance files, verification pipelines before accepting generated changes, and a preference for explicit and strongly typed dependency injection over hidden global states. This will increase the quality of the generated code and improve the whole process, including the code review.

\medskip
\noindent \textbf{Out of scope.} To keep expectations explicit: the project does not port existing agendas to the new stack. The demonstrative mini-app is written for an existing agenda, but the agenda itself is not rewritten. The licensing data model is prepared for reuse by other M-line products, but its adoption in those products is not part of the project. The customer rollout ends with one pilot site switched to the new shell. The full rollout is a follow-up activity of the company. The project adds no new business functionality to the agendas themselves.

\medskip
The description below reflects the current plan. The project runs inside a living company environment, so priorities may shift as the work progresses. Significant deviations from this specification will be documented and justified in the final developer documentation.

\subsection{Functional requirements}
\label{sec:fr}

The requirements are grouped by project outcome and numbered for reference. Requirements marked \emph{(nice to have)} come last in each group and may be reduced under time pressure. The rest are considered essential.

\medskip
\noindent \textbf{Shell}
\begin{itemize}
  \item \reqdef{S1} The shell authenticates users against the Caché backend. The backend decides the authentication mode per user: a local EDISON account, a domain account, or the Windows identity without a password.
  \item \reqdef{S2} The shell establishes a company context at login (the last used company by default) and the user can switch companies at runtime, which closes open agenda windows first.
  \item \reqdef{S3} The shell presents a tree of available modules (agendas), filtered by the customer license and the user's permissions.
  \item \reqdef{S4} The module tree supports text search.
  \item \reqdef{S5} The user can mark favorite modules for quick access.
  \item \reqdef{S6} Every still-relevant legacy WinForms agenda can be launched through a compatibility bridge that passes the established session and company context. The list of agendas that count as still relevant will be fixed with the company by the shell prototype milestone (MS3) and becomes part of the documentation.
  \item \reqdef{S7} Per-user settings (layout, favorites, last company) persist and are restored on the next login.
  \item \reqdef{S8} The shell handles the session lifecycle cleanly: inactivity and forced logout with a user-visible countdown, detection of connection loss, and orderly shutdown.
  \item \reqdef{S9} The shell verifies client/server version compatibility before and during a session. A mismatch triggers the mandatory update (\req{U1}), and the shell refuses to operate only when the update cannot proceed.
  \item \reqdef{S10} \emph{(nice to have)} Desktop shortcuts can start the shell and open a specific agenda directly.
  \item \reqdef{S11} \emph{(nice to have)} Session status information (user, company, client version, license expiry) is persistently visible in the main window.
\end{itemize}

\noindent \textbf{Mini-apps}
\begin{itemize}
  \item \reqdef{M1} The shell provides a hosting area where mini-apps can be arranged and resized, always remaining under shell management.
  \item \reqdef{M2} Agendas opt in by implementing a defined mini-app interface through which they publish their views instead of drawing into the shell directly.
  \item \reqdef{M3} Mini-apps are chosen per user: each user adds and removes them directly in the shell, and the choice persists per user and company.
  \item \reqdef{M4} A mini-app is offered only when its parent agenda is licensed and accessible to the user.
  \item \reqdef{M5} At least one demonstrative mini-app working over real agenda data is delivered.
  \item \reqdef{M6} \emph{(nice to have)} The user's mini-app layout persists per user and company across sessions.
\end{itemize}

\noindent \textbf{Licensing.} By licensing data we mean, per customer: the license itself (type and validity period), the purchased set of licensable features (modules and elements within them), and numeric limits (most importantly concurrent logins). The licenser edits licenses, developers define which elements belong to which licensable feature, and the shell consumes the result at login through the customer backend. Today the license is an opaque encrypted record in the customer's Caché backend, delivered automatically from M-line's central license archive, and the module tree definitions are XML files distributed with the client. The pain is not the distribution but the format and the tooling around it: the encrypted record has no workable data model behind it, and both the licenser and the developers maintain their parts with tools that have not aged well.
\begin{itemize}
  \item \reqdef{L1} Licensing data gets a new, structured data model and store in M-line's central archive, replacing the opaque encrypted format, and the new store plugs into the existing delivery to customer backends. The shell keeps reading the license from the customer backend.
  \item \reqdef{L2} The shell consumes the license: it hides unlicensed modules, presents login rejections when the concurrent-user limit is exceeded, and shows non-blocking warnings for approaching limits and expiry.
  \item \reqdef{L3} An editor for the licenser covers the common workflows, creating, modifying, and issuing customer licenses, and follows the conventions of the company's newer internal tools. Less common cases may stay in the legacy tool for a time.
  \item \reqdef{L4} The module tree definitions (which elements belong to which licensable feature, where a module sits in the tree) move from the XML files distributed with the client into the customer's Caché backend, and developers get a supported way to edit them, replacing today's manual XML maintenance.
  \item \reqdef{L5} Existing licenses are migrated from the old store into the new data model with verified equivalence: a customer installation sees the same modules before and after the migration.
  \item \reqdef{L6} \emph{(nice to have)} The licensing data model is designed product-agnostically so other M-line products can adopt it later.
\end{itemize}

\noindent \textbf{Update mechanism}
\begin{itemize}
  \item \reqdef{U1} At startup the client compares its version with the server installation and, on a mismatch, enforces a mandatory update before letting the user in. The download and apply steps may be carried out by the existing update engine. Replacing it is possible but not promised.
  \item \reqdef{U2} A runtime version guard rejects requests from stale clients, so client and server code never drift within a session.
  \item \reqdef{U3} The server-side release distribution is modernized so that new and legacy clients are served from the same pipeline.
  \item \reqdef{U4} The new update mechanism coexists with the legacy one: legacy clients on the same installation keep updating unchanged.
  \item \reqdef{U5} The client can passively notify the user that a newer release exists without forcing installation.
\end{itemize}

\noindent \textbf{Toolkit.} The toolkit's users are developers, so the requirements below describe what it must offer them.
\begin{itemize}
  \item \reqdef{T1} A view-model base with command creation, unified error presentation, and backend access, keeping view models free of UI-framework references.
  \item \reqdef{T2} Common controls: a server-driven data list with filtering and column persistence, input forms, toolbars, standard dialogs, and a progress overlay.
  \item \reqdef{T3} Theming through shared design tokens, with a light and a dark theme.
  \item \reqdef{T4} A typed backend-access layer wrapping the Caché communication, with one shared session per client process.
  \item \reqdef{T5} A persistence service for per-user and per-company preferences.
  \item \reqdef{T6} A documented usage guide and test patterns for future agenda implementations.
\end{itemize}

\subsection{Non-Functional requirements}
\label{sec:nfr}

\begin{itemize}
  \item \reqdef{N1} Backward compatibility: no breaking changes to the legacy client-server contract, and the same Caché backend serves old and new clients simultaneously.
  \item \reqdef{N2} Parallel operation: the new and the legacy shell are installable and runnable side by side on one workstation and one installation.
  \item \reqdef{N3} Testability: all testable public logic of the toolkit and the shell (view models, services, non-visual components) is covered by unit tests on both stacks, and the tests run automatically before every push.
  \item \reqdef{N4} Extensibility: adding a new agenda requires only its registration, not changes to the shell. Building a first agenda screen with the toolkit should be a matter of days, not weeks.
  \item \reqdef{N5} Server-side configurability: behavior that changes per deployment or per customer (the module tree, licensing) lives in a database, not in the client binaries, so changing it does not require redistributing clients.
  \item \reqdef{N6} Performance: shell startup and agenda launch are not perceptibly slower than in the legacy shell.
  \item \reqdef{N7} Localization: the UI is Czech. Multi-language support is not a goal of the project.
  \item \reqdef{N8} Theming: the light and dark themes are consistent across the shell, the toolkit, and mini-apps.
  \item \reqdef{N9} Platform: Windows 10/11 desktop, distributed through the company's existing release channel.
  \item \reqdef{N10} AI-assistant friendliness: in-repo guidance files, explicit and strongly typed dependency injection as the default for new code, global state limited to a few documented and test-resettable seams, and a verification pipeline before accepting generated changes.
  \item \reqdef{N11} Security: licensing data in the new store is validated server-side, stored credentials are encrypted, and a failed update must leave the client startable. Full tamper-resistance of the license is explicitly out of reach while \req{N1} holds, because legacy clients must keep reading the compatible format.
\end{itemize}

\subsection{Architecture}
\label{sec:architecture}

The solution consists of three cooperating parts, shown as containers in figure~\ref{fig:c4-container}:

\begin{itemize}
  \item \textbf{Modernized shell} -- the client application: login and session lifecycle, company selection, the module tree, launching agendas, and hosting mini-apps.
  \item \textbf{Shared toolkit} -- a library of reusable UI components, view-model infrastructure, theming, and the typed backend-access layer. Consumed by the shell, by TemplateDesigner, and by all future agenda implementations.
  \item \textbf{Legacy bridge} -- a backward-compatibility layer that hosts the existing WinForms agendas and passes them the established session and company context, so that the new shell can launch them without touching their source code. This is not a trivial layer: some agendas need specific exceptions in the host because of their age and the versions of standard components they use.
\end{itemize}

Agendas integrate with the shell through the mini-app interface: an agenda registers a factory for its mini-app view, and the shell instantiates the view, docks it, and manages its lifecycle and license gating. The shell never depends on concrete agendas. Each agenda only implements the interface the shell publishes.

The choice of WPF over WinForms matters especially for mini-apps and theming. Data binding, templating, and view composability make it natural to embed many small live views inside one window and to restyle them centrally. The legacy shell could only approximate this, which is why its capability of surfacing agenda information has stayed so limited.

Two constraints shape the architecture throughout. First, no breaking changes to the legacy contract are permitted, which is why the legacy bridge exists as a separate layer and why both shells must keep working against the same backend during the transition. Second, deploying a database-side change is much faster than redistributing clients, so anything expected to change per deployment or per customer (the module tree, licensing data) belongs to a database rather than to the client. This is the direct motivation for requirements \req{L1} and \req{N5}. On the client, one shared backend session per shell process is a design rule: agendas and mini-apps hosted by the shell reuse the session established at login instead of opening their own. TemplateDesigner currently keeps a session of its own, a temporary consequence of being built while the new stack matures, and will converge to the shared rule. It does not consume an extra license seat, because concurrency is counted per workstation.

The update work is a recreation of the orchestration around updates: when a version mismatch is detected, how the mandatory update is enforced, and how it cooperates with the session lifecycle. The existing logic is too tangled to modify incrementally, and its behavior is entangled with the user-inactivity issues mentioned earlier. The low-level apply engine may be retained (\req{U1}). Update packages live as files on the customer installation's server, from where both shells update themselves. M-line delivers releases to customer servers through the existing channel, modernized so that one pipeline serves both clients (\req{U3}). The new mechanism must leave the legacy clients' update path untouched (\req{U4}).

\section{Platform and technologies}
\label{sec:platform}

\begin{itemize}
  \item \textbf{Client}: C\# on \href{https://dotnet.microsoft.com/}{.NET} (a current LTS release), \href{https://learn.microsoft.com/en-us/dotnet/desktop/wpf/}{WPF}, the \href{https://learn.microsoft.com/en-us/dotnet/architecture/maui/mvvm}{MVVM} pattern.
  \item \textbf{Backend}: \href{https://www.intersystems.com/products/cache/}{InterSystems Caché} and its ObjectScript language; communication over HTTP through the company's existing REST-style channel.
  \item \textbf{Testing}: \href{https://xunit.net/}{xUnit} and \href{https://nsubstitute.github.io/}{NSubstitute} on .NET; the native unit-testing facilities on Caché.
  \item \textbf{Mini-app hosting}: an established WPF docking/layout library. The concrete choice is an implementation decision.
  \item \textbf{License editor}: a web-based internal tool, following the platform of the company's newer internal tools.
  \item \textbf{Development}: Git and GitHub with automated test execution hooked into the workflow; AI coding assistants with in-repo guidance files.
\end{itemize}

\noindent This is not a definitive list, and lower-level libraries will be chosen as the work progresses.

\section{Evaluation}
\label{sec:evaluation}

The evaluation follows the three kinds of outcomes the project produces: code, a deployed product, and a toolkit for developers.

\medskip
\noindent \textbf{Automated testing.} All testable public logic of the toolkit and the shell ships with unit tests on both stacks, and the tests run automatically before every push (\req{N3}).

\medskip
\noindent \textbf{Pilot deployment.} The success criteria are directly measurable: all M-line developer workstations use the new shell as their default daily tool, at least one customer pilot site uses the new shell as its only shell, and all still-relevant legacy agendas remain launchable through the new shell.

\medskip
\noindent \textbf{Developer study.} The toolkit's users are developers, so the user study takes place inside the company: structured feedback will be collected from the M-line developers who consume the toolkit, that is, the author's colleagues working on the shell and the author of TemplateDesigner. The feedback covers API usability, the effort of building a first screen with the toolkit compared to the legacy stack, and the quality of the documentation and test patterns. The expectation the toolkit is measured against is the one stated in \req{N4}: a first agenda screen should be a matter of days, not weeks. Since porting agendas is out of scope, this is measured on the screens actually built with the toolkit during the project: the demonstrative mini-app and the TemplateDesigner screens adopting it.

\section{Risks}
\label{sec:risks}

\begin{itemize}
  \item \textbf{Breaking the legacy contract.} A change on the shared backend could break legacy agendas at customer sites. Mitigation: the legacy bridge isolates the old code instead of modifying it, whether all legacy agendas remain launchable is checked continuously during development, and questions about legacy behavior go to the consultant, who knows that part of the stack best.
  \item \textbf{Update mechanism underestimated.} The legacy updater's behavior is tangled and partly undocumented, and the plan is a full recreation. Mitigation: the new mechanism is used internally long before any customer sees it. Fallback: the legacy updater is a plain file copy and can distribute the new client as well, so the rest of the project does not block on the new mechanism.
  \item \textbf{Licensing migration underestimated.} The old license format is opaque and part of its semantics exists only in the code that reads and writes it. Mitigation: the migration is verified by the equivalence check from \req{L5}, and the data model comes before the editor. Fallback: the old store and its delivery keep running untouched until the equivalence is proven, so the migration can be re-run until it is right.
  \item \textbf{Problems at the pilot site.} The pilot does not depend on a customer volunteering: the company deploys the new shell to a selected site as part of a regular update, not as an opt-in, at least for a time. The real risk is an issue severe enough to send the site back to the legacy shell. Mitigation: months of daily internal use precede the pilot, and both shells stay installed side by side (\req{N2}), so a temporary return is cheap.
  \item \textbf{Toolkit validated by only two consumers.} An API that fits the shell and TemplateDesigner may still not generalize to future agendas. Mitigation: the API is treated as provisional and versioned, design reviews are held with the TemplateDesigner author, and the feedback collected in the evaluation is used to correct the design.
  \item \textbf{AI-generated code quality.} Extensive use of AI assistants risks subtle defects at scale. Mitigation: generated changes go through the same tests and code review as any other change, and the concrete rules that keep the assistants reliable (in-repo guidance files, verification steps required before a change is accepted, conventions such as explicit typed dependency injection) are written down and become part of the AI documentation.
  \item \textbf{Scope and timeline pressure.} The licensing or update work may slip. Mitigation: the schedule puts the foundation first (testing, toolkit, shell), and each outcome can be reduced to a smaller but still useful version. For licensing, the data model and migration come before the editor.
  \item \textbf{Company priorities.} As an employee, the author can be pulled to urgent company work. Mitigation: the milestones are agreed with the company, progress is followed by the author's manager, and the schedule keeps a buffer before the project end.
\end{itemize}

\section{Milestones / Deliverables}
\label{sec:milestones}

The work is structured into seven milestones, each ending with something demonstrable:

\begin{itemize}
  \item \textbf{MS1 Testing infrastructure} -- test projects on both stacks wired into the development workflow.
  \item \textbf{MS2 Toolkit foundation} -- the core components, theming, and backend access, exercised by a first minimal version of the shell.
  \item \textbf{MS3 Shell prototype} -- login, module tree, and launching legacy agendas, all in daily use on developer machines.
  \item \textbf{MS4 Mini-app subsystem} -- the mini-app interface and hosting, with the demonstrative mini-app running over real data.
  \item \textbf{MS5 Licensing modernization} -- the new data model and store in place, existing licenses migrated with verified equivalence, tooling usable by the licenser and developers.
  \item \textbf{MS6 Update mechanism} -- the new client detects a version mismatch and updates itself from the customer server.
  \item \textbf{MS7 Pilot deployment} -- all developer workstations on the new shell by default and a customer pilot site using only the new shell.
\end{itemize}

\noindent The academic deliverable consists of:
\begin{itemize}
  \item \textbf{Source code} of the modernized client shell, the supporting toolkit library, the demonstrative mini-app, the supporting test projects, and any internal tools modified or created during the project where the changes are substantial.
  \item \textbf{Developer documentation}: architectural overview, toolkit usage guide, and recommended development setup for future agenda implementations.
  \item \textbf{AI documentation}: patterns, guardrails, and observations collected during the project, delivered either as a standalone document or integrated with the developer documentation.
  \item \textbf{User documentation} for the new shell, written for end users and primarily highlighting new features and differences from the old shell.
\end{itemize}

The project is developed in M-line's private GitHub repositories (the license editor lives in a separate repository from the client work), so the delivery is a snapshot rather than the full repositories:
\begin{itemize}
  \item Source code and documentation files written by the author
  \item A document specifying files that were also developed by others, describing what was done by the author
  \item An export of the git history of the author, using git log
\end{itemize}
The academic supervisor, opponent, and Committee receive access to the above on request. A demo of the project will also be made accessible upon request, and the functionality will be demonstrated at the defense. M-line software s.r.o. has approved the project scope and consents to its academic delivery and presentation as described here and in the proposal.
